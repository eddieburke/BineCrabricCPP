# Shader parity and performance review

Reviewed 2026-09-06 against the working source and the checked-in `third_party/iris` reference. This is an audit, not an implementation change. Engine and shader-pack sources were left untouched. The earlier handoff's closed sky, stars, sun, bloom, and shadow-sampler investigations were not reopened.

The strongest new findings are in custom-uniform evaluation. Matching directive names and compiling shader programs does not verify expression semantics.

For a symmetric orthographic box with half-extent D on all three axes, `abs(det) = 1 / D^3`. D=1024 and D=2048 do **not** trip the guard; D=4096 does. General shadow-camera behavior also depends on the near/far span, which is configured separately. **Performance opportunities that can preserve parity**

1. Remove recurring evaluator allocations. Every function call currently creates a temporary argument vector, and every frame clears and reconstructs the custom-value hash-map nodes. Resolve references and allocate value/argument storage when compiling the expressions; keep the same per-frame evaluation and stateful-call behavior. Preserve dependency and missing-name semantics deliberately rather than simply retaining last frame's values. Source inspection establishes these allocation sites; their frame-time cost has not been profiled.
2. Build per-program lists of active custom-uniform locations once. The upload loop currently walks every custom declaration for each upload, including uniforms absent from that program. This can reduce CPU lookup work without changing values. `ShaderProgram::location` already caches locations, including misses, and world-program uploads already have a generation guard. Claims of a driver location query or a complete uniform upload on every draw would therefore be wrong. Relink and pack reload must invalidate any new lists.
3. Profile the dawn/dusk workload before changing scheduling. [ChunkSectionSystem.cpp:444](<C:/Users/Eddie/Documents/New project 2/src/net/minecraft/client/render/world/ChunkSectionSystem.cpp:444>) invalidates sky-lit sections in one sweep. However, [ChunkCompilePipeline.cpp:113](<C:/Users/Eddie/Documents/New project 2/src/net/minecraft/client/render/world/ChunkCompilePipeline.cpp:113>) already budgets capture/upload work and prioritizes nearby and visible sections. Remaining candidates include the invalidation sweep, repeated candidate scans, and minimum item counts that may exceed a time budget. Measure their contributions before calling this the cause of hard stalls. Skipping remeshing outright requires proving that mesh bytes, lighting, and mod outputs do not depend on ambient darkness.

No FPS gain or stall reduction is claimed. No optimization was applied during this audit.

**Validation and implementation order**

The existing `minecraft_omega_tests.exe` passed all seven selected tests: five `CustomUniformsTest` cases, `ChunkCompilePriority.VisibleSectionsPrecedeCloserInvisibleSections`, and `FogModeParity.CustomUniformsFogModeMatchesFrameValue`. The initial run could not create `%APPDATA%/.minecraft/mods/.cache`; rerunning with a process-local APPDATA under this audit's `runtime` directory succeeded. The user profile was not modified by the successful run.

The existing tests do not cover the new counterexamples. In particular, `SmoothAndArithmetic` samples a constant once, so it cannot detect timing or shared-history defects. No native build, new C++ regression run, or in-game A/B comparison was performed. Source inspection establishes the listed differences; numerical checks establish selected consequences; visible impact and performance magnitude remain unmeasured.

Recommended order: fix `smooth` overloads, timing, and per-call storage together; then match ordinary `if` branch evaluation; then address type-directed arithmetic, exact comparisons, and dependency ordering. Assign smooth state to a stable compiled call site before making `if` lazy, otherwise the current evaluation-order-generated IDs would shift when branches change. Do not automatically short-circuit `&&` or `||`: the checked-in Iris `BB2BFunction` evaluates both operands. Multi-condition `if` has its own unusual reference implementation and needs separate parity cases.

Cover duplicate IDs, literal-ID overloads, zero fade, changing branches, forward references, cycles, odd viewport widths, exact comparisons, and valid small-determinant matrices with targeted native regressions. For storage and upload optimizations, compare per-frame/per-program uniform values before and after, and measure allocations and CPU time separately.
